# Как идёт работа: координатор, агенты, корпус, выкладка

Этот файл — рабочая память проекта. В нём всё, что нужно новой сессии (или другому ИИ), чтобы продолжить работу без предыдущих чатов. Правила содержания — в `PRINCIPLES.md`; здесь — **кто что делает и в каком порядке**.

## 2. Цикл главы (решения владельца)

**Правила строго обязательны** (слово владельца 11.11.2026, `PRINCIPLES.md` §9.6). Норма не выполнена — глава не готова; доделать до PR, а не объяснять в отчёте. «Не сделал» или «превышено» в отчёте агента — недоделка координатора: вернуть агенту на доработку. Правило выполнить нельзя — остановиться и спросить владельца. Перед словом «готово» — чек-лист §9.6, пункт за пунктом.


1. **Выбор главы** — сверху вниз по очереди в `docs/NIGHT-QUEUE.md`; порядок изучения — `COURSE_ORDER` в `src/data/corpus/levels.js`.
2. **Автор пишет главу.** Задание координатора: id главы, название, место в курсе (что уже изучено, что нет), границы с соседними главами, рекомендованный состав уроков, префикс имён. Остальное автор берёт из своей инструкции и `CHAPTER_BRIEF.md`.
3. **Автоматическая проверка:** `node tools/check-chapter.js <id>` — 0 ошибок и 0 предупреждений (кроме ложных срабатываний, доказанных в заметках главы).
4. **Одна проверка одним агентом.** Проверяющему дают только id главы и замечания автора о спорных местах. Отчёт он дописывает в заметки главы `docs/plans/<id>.md`, раздел «Проверка» (заметки главы — один файл).
5. **Одно исправление** — тот же автор (продолжить его, а не запускать нового), по разделу «Проверка», исправляется **всё**: ошибки, важное и мелочи. Координатор добавляет свои решения по спорным пунктам и после исправления сам сверяет по списку, что каждый пункт закрыт.
6. **Подключение и тесты** — координатор:
   - `tools/build.py`: файлы главы (lessons, bank, classic, tests, index — перед `nn/labs.js`; labs — в блок схем);
   - `src/js/core/store.js`: `ready:1` у главы;
   - `python3 tools/build.py`, `node tools/test/smoke.js`, `node tools/test/layout.js` — без ошибок, перед **каждым** коммитом, и в рабочей ветке тоже;
   - открыть главу в браузере (все четыре вкладки, 390 и 1440 px), посмотреть скриншот.
7. **Документы:** `CLAUDE.md` («Что готово»), `NIGHT-QUEUE.md` (очередь и журнал), `ROADMAP.md`, заметки главы.
8. **Выкладка:** коммит → PR в `main` → слить → проверить сайт → вернуть рабочую ветку на `origin/main`.
9. **Отчёт владельцу:** что сделано, что нашла проверка, что не вошло и почему, вопросы.

Не больше двух глав за ночь. Вторую проверку и нескольких проверяющих не запускать (экономия лимитов).

## 4. Git и выкладка

- Рабочая ветка — та, что назначена сессии; PR в `main`; после зелёных тестов координатор сливает PR сам (владелец просил его не ждать). Сайт обновляется автоматически: https://veracerkof-debug.github.io/interactive.russian/
- После слияния: `git fetch origin main && git checkout -f -B <ветка> origin/main && git push -f -u origin <ветка>`.
- Перед коммитом вернуть собранные файлы: `git checkout dist` (в git лежит только `dist/index.html`; он пересобирается при выкладке).
- Черновик главы до проверки можно коммитить в рабочую ветку (после сборки и тестов), но не сливать в `main`.
- В сообщениях коммитов и PR — без названий моделей в тексте; подписи — как задаёт среда.
- Корпус `korpus.knig` — прямые коммиты в `main` (личный репозиторий владельца).

## 5. Ночная работа

Запланированное задание «Ночная работа над учебником» — каждую ночь в 0:00 по Самарканду, до 5:00, не больше двух глав. Текст задания хранится в расписании; его смысл — раздел 2 этого файла. Незаконченное к 4:45 — закоммитить в рабочую ветку с пометкой «в работе» в очереди. Утром — краткий отчёт владельцу.

Владелец может остановить работу («стоп», «до среды») — тогда задание выключается и ставится напоминание включить его обратно.

## 6. Что мы узнали на практике

- **Без источников ИИ уверенно ошибается.** Попытка с другим ИИ дала неверные правила и транскрипции, сломанный код. Поэтому — корпус, словари и отдельный проверяющий.
- **Проверяющий в каждой главе находит 9–15 ошибок.** Типичные: два верных ответа в задании, неверный ключ, изменённая цитата, повторы слов, термины за границей знаний.
- **Цитаты — только из корпуса, сверка скриптом.** Взятые по памяти приходится проверять отдельно.
- **Лимиты.** Агент может остановиться посреди работы. Его работа сохранена в файлах: закоммитить промежуточное состояние, после обновления лимита продолжить **того же** агента сообщением «продолжай, сначала сверь по списку, что уже сделано».
- **Отчёт проверки — в файл заметок главы**, иначе его нечем передать автору.
- **Два автора одновременно** могут править `glossary.js` — только точечные вставки; примеры-дубли между соседними главами разводит координатор.
- **Корпус правится по опыту каждой главы:** что не нашлось или мешало — исправить в корпусе сразу после главы.
- **Интерфейс** (главная, кабинет, навигация) делает отдельный агент по подробному заданию координатора; перед этим — короткий обзор, как сделано у других и на что жалуются; после — скриншоты на телефоне и компьютере, в светлой и тёмной теме; пороги и спорные решения — вопросами владельцу в `docs/plans/<тема>.md`.
